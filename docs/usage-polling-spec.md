## 1. 定期的に自動で走るもの

| 何が | 間隔 | 定義場所 | ネットワーク |
|---|---|---|---|
| トレイの使用量更新（`tray::refresh`） | **60秒** | `tray.rs:44` `REFRESH_INTERVAL` | 条件付き（下記4の2層のゲートを通ったときだけ） |
| 自動アップデート確認 | 起動15秒後 → 以降**12時間**ごと | `updater.rs:13,14` | あり（GitHub） |
| token 自動復帰の裏起動（期限切れ検知時のみ） | 発火は最短**10分**間隔 | `actions.rs:1151` `TOKEN_NUDGE_MIN_INTERVAL` | `claude` CLI 経由 |

**［確認］** これ以外に定期実行はない。フロントエンド（`src/`）に使用量のポーリングは無く、`setInterval` は2箇所ともアカウント追加フローの一時的なものだけ。

60秒サイクルの中身は順に:
1. `auto_sync_live()` — ライブ Keychain を読み、ハッシュが前回と違えば持ち主確認（下記2-3）
2. `get_accounts_usage(force=false)` — 登録アカウントの使用量照会（ゲートを通ったものだけ）
3. トレイメニューの再構築

**トレイのループが60秒なのは、メニュー再構築とライブ資格情報の変化検知がローカル処理だから。ネットワーク照会の頻度はこれとは別に制御されている（下記4）。**

## 2. ネットワークアクセスの全経路

### 2-1. `GET https://api.anthropic.com/api/oauth/usage`

**［確認］** `actions.rs:172` 付近に URL 定義。呼び出しは3箇所で、**すべて試行間隔ゲートを通る**。

| 呼び出し | 使うトークン | ゲートのキー |
|---|---|---|
| `accounts.rs` ライブ枠 | ライブ Keychain（`Claude Code-credentials`） | `<name>:live` |
| `accounts.rs` スナップショット枠 | `CC Anatomy-cred-<name>` | `<name>:snapshot` |
| `tray.rs` フォールバック | ライブ Keychain | `__live_fallback__` |

`tray.rs` のフォールバックは、ライブアカウントが登録済みアカウント一覧に居ないときだけ使う（未取り込みの初回起動・org_id 不一致・`has_credentials=false`・**Windows/Linux 全体**）。

ライブ枠とスナップショット枠でキーを分けているのは、429 以外の理由でライブ直叩きが失敗したときのフォールバック連鎖を塞がないため。**同じアカウント・同じエンドポイントなので同じレート制限の枠を食う**が、実際に1つの窓で2回叩く条件は狭い（429 なら同一サイクル内フラグで止まる／期限切れならゲートを消費せず抜ける／通信断なら両方落ちる）。最悪でもアカウントあたり5分に2回。

### 2-2. `POST https://api.anthropic.com/v1/messages` ← 使用量を消費する

**［確認］** `{"model":"claude-haiku-4-5-20251001","max_tokens":1,"messages":[{"role":"user","content":"hi"}]}` を投げ、レスポンスヘッダ `anthropic-ratelimit-unified-*` から使用率を読む。

**これは実際の推論リクエストで、使用量を消費する。ゲートの対象外。**

使うトークンは監視用長期トークン `CC Anatomy-token-<name>`（`sk-ant-oat01...`、108文字）。

取得元の優先順位（`accounts.rs` の `resolve_usage_source_order`）:

- **ライブ**: `/api/oauth/usage` →（失敗したら）`/v1/messages` →（さらに失敗したら）スナップショットで `/api/oauth/usage`
- **非ライブ**: `/v1/messages` が最優先 → スナップショットで `/api/oauth/usage`

したがって非ライブ2アカウントは、600秒ごとに1回ずつ推論リクエストを投げている。

**［未確認］** 1リクエストあたりの使用量への寄与。`max_tokens:1` なので極小のはずだが、ゼロではない。

### 2-3. `GET https://api.anthropic.com/api/oauth/profile`

**［確認］** ライブ Keychain の access token を使う。ゲートの対象外。

呼ばれるのは、ライブ資格情報の SHA-256 ハッシュが前回記録（`last_live_hash` / `last_checked_hash`）と**違うとき**だけ。つまり **Claude Code が token を refresh するたびに1回**。定期実行ではない。

### 2-4. GitHub（自動アップデート）

12時間ごと。Anthropic の使用量とは無関係。

## 4. 照会を控える仕組み（2層）

**［確認］** 目的の違う2つの仕組みがある。片方だけでは足りない。

### 層1: キャッシュ新鮮判定（`cache_is_fresh_enough`）

「前回**成功した**取得からの経過時間」が閾値未満なら、そもそも照会しない。

- ライブ **300秒**（`actions.rs:172` `USAGE_MIN_REFETCH_SECS`）
- 非ライブ **600秒**（`actions.rs:192` `NON_LIVE_MIN_REFETCH_SECS`）
- `force=true` は**ライブの判定だけ**をスキップする（非ライブは force でも600秒）

### 層2: 試行間隔ゲート（`gate_usage_attempt`）

「最後に**試行した**時刻」からの経過時間が閾値未満なら、HTTP を打たない。**成否にかかわらず試行時点で記録する。**

閾値は `usage_attempt_min_interval(is_live, force)`（`actions.rs:212`）:

| | force=false | force=true |
|---|---|---|
| ライブ | 300秒 | **45秒** |
| 非ライブ | 600秒 | 600秒（force の効果なし） |

手動経路が45秒なのは、60秒だと `REFRESH_INTERVAL` と同値になり到達時刻の揺れで通ったり弾かれたりするため。

### なぜ2層要るか

層1だけだと、**取得に失敗し続ける間はキャッシュが古いままなので毎サイクル叩いてしまう**。いちばん間隔を空けたい場面（429 が続いているとき）でスロットルが消える。これは v0.5.3 の実際の挙動だった。

**［重要］`usage_cache.fetched_at` を失敗時に更新して層2の代わりにしてはならない。** 下記6の注記の判定が壊れる。試行時刻（`USAGE_LAST_ATTEMPT`）は別の状態として持っている。

### ゲートで塞いだときに何を表示するか

「ゲートに塞がれた」ことと「なぜ取得できなかったか」は別物。前者を後者として表示すると事実と違う案内になる（HTTP を1回も打っていないのに「取得が一時的に制限されています」と言う等）。

そのため `USAGE_LAST_ERROR` に**直近に実際に試行して分かった失敗理由**を保持し、ゲートで塞いだときはそれを返す（`actions.rs` の `resolve_gated_error`）。成功したら消す。

## 5. トークンの種類と、認証切れが起きうる箇所

| トークン | 保管先 | 有効期限 | 誰が更新するか |
|---|---|---|---|
| ライブ access token | Keychain `Claude Code-credentials` | **約8時間** | **Claude Code 本体のみ** |
| ライブ refresh token | 同上（同じ JSON 内） | **ログインから約2週間の絶対期限** | **Claude Code 本体のみ**。one-time use |
| スナップショット access token | Keychain `CC Anatomy-cred-<name>` | 取得時点から**約8時間** | **誰も更新しない** |
| 監視用長期トークン | Keychain `CC Anatomy-token-<name>` | 記録上は1年 | 更新の概念なし。失効したら再発行 |

**［確認］アプリが refresh token を使って refresh する箇所は無い。**

**［確認］refresh しても refresh token の期限は延びない。** 同一アカウントで access token が 14:38 → 22:33 に更新された前後で、`refreshTokenExpiresAt` は 08/31 17:01 のまま動かなかった。つまりログイン時点から約2週間の絶対的な締め切りがあり、**それを過ぎたら再ログインが必須**。

### 認証切れが起きうる箇所

**A. スナップショットの期限切れ（日常的・仕様）**
最後にライブだった時刻から約8時間で切れる。切れると `/api/oauth/usage` は打てず、監視トークン経由に落ちる。切り替えれば Claude Code が refresh して復活する。

**B. 切り替えによる refresh token の巻き戻し（設計上の最大リスク）**
切り替えは Keychain の `Claude Code-credentials` を**スナップショット JSON でまるごと上書き**する。この JSON には refresh token が含まれる。one-time use なので、スナップショットを取ったあとに Claude Code がその refresh token を使っていた場合、古いものを書き戻すと**そのアカウントは refresh 不能になり再ログインが必要**になる。

防止策が切り替え直前の sync-back。ただし持ち主を確認できない（token 期限切れ・通信不能・**429**）と飛ばされる。**429 は `NetworkError` に分類され「持ち主未確認だが続行可」側に倒れる**ので、続行を選ぶとこのリスクを踏みうる（そうしないと切り替え自体が不能になるため意図的）。

**C. refresh token の絶対期限切れ**
約2週間切り替えていないアカウントは、access token だけでなく refresh token も切れる。この状態では切り替えても復活せず、`claude auth login` からやり直しになる。

## 6. 注記と表示

### 注記（値は出せているが、古いかもしれないとき）

**［確認］** 判定は `tray.rs` の `usage_advisory`。**`live_error`（直叩きが失敗したか）ではなく、表示に使っている値の古さで判定する。**

- `now - fetched_at` が **600秒**（`actions.rs:232` `USAGE_STALE_NOTE_SECS`）以下 → **注記なし**
- 超えている → `HH:MM 時点`
- 超えていて、かつ原因が `Expired` → 上に加えて「Claude Code を一度実行すると復帰します」

原因（レート制限・通信不能）は注記に出さない。ユーザーに対処のしようがないため。

**v0.5.3 の「取得が一時的に制限されています（最新でない可能性）」という注記は廃止した。** 別のソースが新鮮な値を取れていても出てしまい、文言と事実が食い違っていたため。

### 値がまったく無いときの案内（Blocking）

**［確認］** 従来どおり原因ごとに2行:

| 原因 | 1行目 | 2行目 |
|---|---|---|
| `Expired` | token 期限切れ | Claude Code を一度実行すると復帰します |
| `RateLimited` | 使用量を取得できません | 取得が一時的に制限されています。しばらくお待ちください |
| `Network` | 使用量を取得できません | 接続できません。ネットワークを確認してください |
| `Other` / なし | 使用量を取得できません | Claude Code でログインしてください |

### 表示側が使っていない情報

**［確認］** `AccountUsage.stale` は表示に使われていない（`fetched_at` はライブの注記にのみ使う）。

### リセット時刻を過ぎたときの補正

| 表示 | 5h | 週次 | 「〇〇復活」の日時 |
|---|---|---|---|
| ライブ | 補正なし | 補正なし | 補正なし |
| 非ライブ | **0% とみなす**（`five_probably_reset`） | 補正なし | 補正なし（過去の日時が出続ける） |

**未対応。** 復活日時を過ぎても週次は古い % が残り、日時表示は過去のまま。

## 8. アカウント切り替えの処理順

**［確認］** `accounts.rs::switch_account`

1. 本アプリ自身の子プロセス（AI分析・環境診断）実行中ならハードブロック
2. 外部の claude セッション数を `ps` で数え、1件以上なら確認ダイアログ（force で続行可）
3. **sync-back**: ライブ Keychain を読み、ハッシュが前回と違えば `/api/oauth/profile` で持ち主確認 → 一致すればスナップショットへ書き戻す
4. 切り替え先のスナップショットを Keychain から読む
5. **Keychain `Claude Code-credentials` を上書き**
6. `~/.claude.json` の `oauthAccount` を差し替え（一時ファイル経由の atomic rename）
7. 検証。失敗したらロールバック。ロールバックも失敗したら `meta.inconsistent = true`
8. `last_live_hash` を記録して保存

ネットワークを使うのは 3 の profile API だけ。

## 9. 実測で分かっている 429 の性質

**［確認］2026-08-22 実測**

- 429 は**リクエスト頻度**によるもので、**そのアカウントの使用量の枠とは無関係**。5h 枠を 100% 使い切ったアカウント2件が 200 を返す一方、枠に余裕のある（16%）アカウントが 429 を返した
- 枠は**アカウント単位**。非ライブのアカウントはアプリがこのエンドポイントを叩かない（監視トークンが最優先）ため、外部から連続で叩いても影響がない
- 枠は狭い。**8秒間隔で3回叩けば 429 になる**
- 60秒間隔で8回叩いたとき、8回中5回が 429 になった環境がある

**［否定済み］** 「アカウントが使用量の上限に張り付いているのが原因」という仮説は、上記の比較で否定した。
**［未確認］** 「claude セッションがこの枠を共有している」という仮説。裏付けは取れていない。むしろ非ライブのアカウントが影響を受けていないことから、アプリ自身のポーリングが支配的だと考えられる。
**［未確認］** 正確な閾値と回復速度。

## 10. 既知の限界（意図的に残しているもの）

1. **`/v1/messages` は使用量を消費する。** 非ライブの使用量を見るために、10分ごとに推論リクエストを投げている。ここをどうするかは未決定
2. **外部で `claude auth login` して未登録アカウントに変わった場合**、`tray.rs` フォールバックの保持値がアカウント名前空間で分かれていないため、最大300秒（手動なら45秒）だけ前アカウントの数値が出る
3. **失敗が続く状況では、5分ごとに1サイクルだけエラー表示にフラップする。** ゲートで塞がれたサイクルは保持値を返すが、実際に試行して失敗したサイクル（`Failed`）は保持値へフォールバックしないため
4. **`resolve_gated_error(None)` の中立文言は画面に出ない。** この防御的分岐は `LiveUsageError::Other` を返すが、`usage_advisory` の `Other` は文言を無視して「Claude Code でログインしてください」を出す。ただしこの分岐は実際には到達しない（ゲートが消費される時点で成功か失敗のどちらかが記録されている）
5. **週次とライブに「リセット時刻を過ぎたら0%」の補正が無い**（上記6）
